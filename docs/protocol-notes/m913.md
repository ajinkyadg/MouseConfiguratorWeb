# Redragon M913 Impact Elite — USB HID protocol notes

Factual reference for implementing `profiles/m913.ts` from scratch. This
document records only facts about the wire protocol (device IDs, byte
layouts, checksum arithmetic, lookup tables) — it does not reproduce any
source code. The TypeScript implementation should be written directly from
this document, not by translating any existing implementation line-by-line.

**Provenance**: these facts were read out of
[`m913-ctl`](https://github.com/Qehbr/m913-ctl) (GPL-3.0), which itself
states it reverse-engineered the protocol from USB captures and the
`mouse_m908` project. Protocol facts (device IDs, byte offsets, checksum
formulas, encoding tables) are not copyrightable expression, but if this
project is ever open-sourced, get this reasoning checked rather than assume
it.

## Device identification

Two hardware revisions exist in the wild; both need to be probed for.

| Revision | VID | PID (2.4G wireless receiver) | PID (wired / dual-mode) |
|---|---|---|---|
| Areson (original) | `0x25a7` | `0xfa07` | `0xfa08` |
| Compx (newer) | `0x3554` | `0xf55d` | `0xf55e` |

The two revisions use **different DPI and LED wire encodings** (see below) —
detect which one you're talking to from the VID before building any packet.

**These IDs are not exclusive to the M913.** `0x3554` (Compx) is an OEM
vendor ID: the wired PID `3554:f55e` is also reported by the Redragon M917
GB Pro ([libratbag#1854](https://github.com/libratbag/libratbag/issues/1854))
and the K1NG M916 PRO
([universal-mouse-drivers#1](https://github.com/skullboypl/universal-mouse-drivers/issues/1)),
and `25a7:fa07`/`fa08` are also used by the UtechSmart Venus Pro. VID/PID
therefore can't prove a device is an M913; the app checks the USB product
name (`identifyM913()` in `src/core/hid-transport.ts`) and requires an
explicit user confirmation before enabling Apply on anything whose name
doesn't say "M913". The M913's actual product-name string hasn't been
recorded yet — capture it from the connect log (`name="…"`) on real hardware.

**Confirmed, 2026-08-31 (Areson)**: only the **wired** PID (`0xfa08`)
accepts config writes. Connecting via the **wireless receiver** PID
(`0xfa07`) and calling `sendFeatureReport` fails outright ("Failed to
write the feature report") — the receiver appears to only relay standard
mouse input reports (movement/clicks) over the 2.4G link, not the vendor
config channel. The app should detect the PID on connect and tell the
user to plug in the USB cable rather than attempting a doomed write.
Compx's wired/wireless PIDs are assumed to behave the same way but not
yet independently confirmed.

## Transport

The native tool talks to the device via `libusb` control transfers:

- `bmRequestType = 0x21` (host→device, class, interface)
- `bRequest = 0x09` (HID `SET_REPORT`)
- `wValue`:
  - Areson: `0x0308` → HID report type `3` (Feature), report ID `0x08`
  - Compx: `0x0208` → HID report type `2` (Output), report ID `0x08`
- `wIndex = 0x0001`
- Device→host responses come back on interrupt IN endpoint `0x82`.

**WebHID mapping — confirmed for Areson, 2026-08-29**: `HIDDevice.sendFeatureReport(0x08, data)`,
where `data` is the 16-byte payload *without* the leading `0x08` (WebHID's
report-ID argument replaces byte 0 of the raw packet), works against real
Areson hardware — verified via a steady-color LED command taking visible
effect. This also confirms Chrome's WebHID implementation can claim the
Areson feature-report interface directly, with no OS-driver conflict and no
elevation needed — unlike the native app's libusb path.

**Compx mapping — still unverified**: `HIDDevice.sendReport(0x08, data)`
(Output report) is the equivalent inference for Compx hardware, but hasn't
been tested against a real Compx device yet. Don't treat it as confirmed
until it has been.

## Packet structure (17 bytes, host→device)

| Byte | Role |
|---|---|
| 0 | Always `0x08` (config command marker / report ID) |
| 1 | Sub-command: `0x07` = write data, `0x04` = finalize |
| 2 | Always `0x00` |
| 3 | Always `0x00` (except keyboard-key sub-packets, where it's an address byte) |
| 4 | Memory address byte (which block to write) |
| 5 | Payload length (bytes 6..5+len are meaningful) |
| 6–13 | Payload data |
| 14–15 | Padding, always `0x00` |
| 16 | Checksum (see below) |

Device→host response packets use report ID `0x09` at byte 0 instead of
`0x08`.

## Checksums

```
host → device:  byte[16] = (0x55 - sum(bytes[0..15])) & 0xFF
device → host:  byte[16] = (0x4C - sum(bytes[1..15])) & 0xFF   (byte[0] excluded)
```

Several commands below also carry an *inner* checksum on a sub-range of the
payload (e.g. `(0x55 - r - g - b) & 0xFF` for an RGB triplet) — those are
noted inline where they occur; they're separate from the outer byte[16]
checksum, which always covers the whole packet.

## Polling rate

One packet. Register address `0x0000`, length 2.

```
byte[4] = 0x00, byte[5] = 0x02
byte[6] = code       where 1000 Hz→0x01, 500 Hz→0x02, 250 Hz→0x04, 125 Hz→0x08
byte[7] = (0x55 - code) & 0xFF
```

## DPI — Areson hardware

DPI values are **not** arithmetic — they're a lookup table of
(value → 3-byte code). Only known-good values from the table can be set;
there is no formula to derive new codes. A representative subset (extend as
more values are needed):

```
100 →  00 00 55      1000 →  0b 0b 3f      4000 →  2f 2f f7      10000 →  77 77 67
200 →  02 02 51      1200 →  0d 0d 3b      5000 →  3b 3b df      12000 →  8f 8f 37
400 →  04 04 4d      1600 →  12 12 31      6400 →  4c 4c bd      14000 →  a7 a7 07
800 →  09 09 43      2000 →  17 17 27      8000 →  5f 5f 97      16000 →  bd bd db
```
(Full table has ~50 entries at non-uniform steps — see "Next steps" below
for where to source the complete set independently.)

5 DPI slots, packed two-per-packet across 3 packets, plus a 4th packet
carrying the enabled-slot bitmask:

- Packet 0: slot 1 at payload offset 6 (3 bytes, with a 1-byte `0x00` gap
  before the 3rd byte — i.e. bytes 6,7,_,9), slot 2 at offset 10 (same
  layout).
- Packet 1: slot 3 at offset 6, slot 4 at offset 10.
- Packet 2: slot 5 at offset 6 only (4-byte payload).
- Packet 3: enabled-slot control at bytes 6–7. Disabling cascades from the
  top — you can't disable an arbitrary slot, only "slot N and everything
  above it": `{e1,e2}` = `{0x05,0x50}` all 5 on, `{0x04,0x51}` top 4,
  `{0x03,0x52}` top 3, `{0x02,0x53}` top 2, `{0x01,0x54}` only slot 1. At
  least one slot must stay enabled.

3 more packets always follow the 4 DPI packets (called "unknown_2" in
m913-ctl, where they're a constant suffix). They are the **per-stage DPI
indicator colors** — see "DPI indicator colors" below.

## DPI — Compx hardware

Arithmetic, not table-based: `code = (dpi / 50) - 1`. Valid range 50–12750
in steps of 50 (`COMPX_DPI_MIN`/`MAX`/`STEP`).

One packet per slot, `addr = 0x0c + slot_index * 0x04`, payload
`[code, code, 0x00, inner]` where `inner = (0x55 - code - code) & 0xFF`.

Plus a stage-count packet at `addr = 0x02`: payload `[count, (0x55-count)&0xFF]`.
Compx also cascades from the top — count is "how many contiguous stages
starting at slot 1 stay enabled," same rule as Areson.

Compx per-slot DPI colors: one packet per slot at
`addr = 0x2c + slot_index * 0x04`, payload `[r, g, b, (0x55-r-g-b)&0xFF]`
(see next section — the same records Areson writes two at a time).

## DPI indicator colors (both revisions)

> **Inferred from the bytes, not yet verified on hardware.** Nobody has
> changed these and watched the mouse's DPI indicator follow. Treat as
> high-confidence but unconfirmed.

One 4-byte record per DPI stage at `addr = 0x2c + stage_index * 4`
(stages 0–4 → `0x2c, 0x30, 0x34, 0x38, 0x3c`), each
`[r, g, b, (0x55 - r - g - b) & 0xFF]` — the same "record sums to 0x55"
shape as the DPI records at `0x0c + stage*4` and the LED color at `0x54`.

- **Areson** writes them the way it writes DPI values, two per packet:
  `0x2c` (len 8: stages 1+2), `0x34` (len 8: stages 3+4), `0x3c` (len 4:
  stage 5).
- **Compx** writes one record per packet (len 4).

Decoding the old constant "unknown_2" packets with this layout gives five
colors, every inner checksum matching:

| Stage | Record bytes | Color |
|---|---|---|
| 1 | `ff 00 00 56` | `#ff0000` red |
| 2 | `00 00 ff 56` | `#0000ff` blue |
| 3 | `00 ff 00 56` | `#00ff00` green |
| 4 | `ff ff 00 57` | `#ffff00` yellow |
| 5 | `ff 55 7d 84` | `#ff557d` pink |

These are the app's default colors (`DEFAULT_DPI_COLORS`), and a regression
test asserts the default build reproduces the old constant packets byte for
byte, outer checksums included. Cross-check: the UtechSmart Venus Pro
protocol notes (same Areson controller family,
[PROTOCOL.md](https://github.com/Es00bac/UtechSmart-Venus-Pro-Linux-MMO-Mouse-Utility),
MIT) describe DPI records at `0x000c + slot*4` with `sum(record) == 0x55`,
stage count at `0x0002`, and label the region `0x002c–0x005f` as "DPI colors
and lighting configuration" (LED effect at `0x0054`) — consistent with this
layout, though that document doesn't spell out the per-stage color offsets.

## LED

Four modes: Off / Steady / Respiration (breathing) / Rainbow.

- **Off**: one packet, address `0x58`, payload `[0x00, 0x55, 0, 0]`.
- **Steady**: one packet, address `0x54`. Payload: `r, g, b,
  (0x55-r-g-b)&0xFF, 0x01 (mode=steady), 0x54 (=0x55-0x01), brightness,
  (0x55-brightness)&0xFF`.
- **Respiration**: two packets. First (address `0x54`) carries color +
  mode=`0x02`, same layout as Steady but mode byte is `0x02`/checksum
  `0x53`, and bytes 12–13 carry brightness the same way. Second packet
  (address `0x5c`) carries speed: payload `[speed, (0x55-speed)&0xFF]`,
  speed range 1 (slowest) – 5 (fastest).
- **Rainbow**: two fixed packets (addresses `0x54` and `0x5c`) with no
  configurable parameters — constant payloads, not yet worth documenting
  further since there's nothing to compute.

## Button remapping

16 logical buttons, indexed 0–15 in this fixed order: `Side1..Side6, Right,
Left, Side7, Side8, Middle, Fire, Side9..Side12`.

### Mapping packets

8 packets, 2 buttons per packet, addresses stepping by `0x08` from `0x60`
(button index `i` → packet `i/2`, offset `6` if `i` even else `10`, 4 bytes).
Every packet starts from a **default template** (below) and only the
touched buttons' 4-byte slots get overwritten — untouched buttons keep
whatever the template already encodes (their factory action), matching the
native app's "a button left unset keeps its current action" behavior.

Two different default templates exist, selected by hardware revision —
**Areson** (identity index mapping) vs. **Compx** (needs the translation
table below, since Compx's physical-button-to-protocol-index wiring
differs). This is one of the few places Compx needs its own logic even
though it isn't a DPI/LED packet.

**Compx index translation** (button index above → protocol packet slot):
`Side1..5→3..7, Side6→10, Right→1, Left→0, Side7→9, Side8→15, Middle→2,
Fire→8, Side9→14, Side10→13, Side11→12, Side12→11`.

Default template payloads (8 packets × 17 bytes) for each hardware
revision, and the per-button keyboard-key sub-packet address table, are
sizeable raw data — captured in `docs/protocol-notes/m913-button-tables.json`
alongside this doc rather than inline here, to keep this file readable.

### Action code format

4 bytes: `[function_type, byte1, byte2, byte3]`.

- `function_type` in the `0x00`–`0x08` range (see action catalog in the
  JSON tables file) = a fixed mouse/DPI/special action — used as-is, no
  sub-packet needed.
- `function_type = 0x90` = keyboard key (byte1 = modifier bitmask, byte2 =
  HID usage code or 0 if modifier-only, byte3 = multi-key count if >1) —
  **requires** a keyboard-key sub-packet (see below); the mapping slot
  itself just gets the constant marker `05 00 00 50`.
- `function_type = 0x92` = multimedia/consumer key (byte1/byte2/byte3 =
  extra, code, extra2) — also requires a sub-packet, different template.

### Keyboard-key sub-packets

Every keyboard-key binding needs 1–2 extra 17-byte packets sent *before*
the 8 mapping packets, addressed via a lookup table indexed by **protocol
slot** (16 entries, 2 bytes each — `keyboardKeyAddressByProtocolSlot` in
the JSON tables file; for Compx, translate the button to its protocol slot
via `compxIndexTranslation` first — don't index this table by button name
directly, it only looks that way for Areson's identity mapping), encoding
a sequence of HID down/up events:

- **Modifier-only or single plain key** (no modifiers + 1 key, or
  modifiers-only): one sub-packet. Payload: `[0x02, event1_type,
  event1_code, 0x00, event2_type, event2_code, 0x00, inner_checksum]`
  where event1=down, event2=up (same code twice), and
  `inner_checksum = (0x55 - sum(payload[0..6])) & 0xFF`.
- **Modifier+key, or multi-key combo**: two sub-packets carrying an event
  list — one 3-byte event (`type, code, 0x00`) per key-down, in order:
  all-modifiers-down (`0x80`), all-keys-down (`0x81`, in order),
  all-modifiers-up (`0x40`, same order), all-keys-up (`0x41`, **reverse**
  order). Packet 1 holds `event_count` + the first 9 event bytes (3
  events); packet 2 holds the remaining events + a trailing inner
  checksum (`(0x55 - event_count - sum(all event bytes)) & 0xFF`). Hard
  cap: 18 event bytes across both packets ÷ 6 bytes/token (2 events ×
  3 bytes) = **3 modifiers+keys max** per binding.
- **Multimedia key**: one sub-packet, payload
  `[0x02, 0x82, code, extra, 0x42, code, extra2, inner_checksum]`.

### Action catalog

Full action-name → byte-code tables (mouse/special actions, modifier
bits, keyboard HID usage codes) are in
`docs/protocol-notes/m913-button-tables.json` — a straight lookup table,
not a formula, same treatment as the DPI table above.

   not yet recorded for either revision. If it doesn't contain "M913", real
   owners get a confirmation prompt on every connect — record the string
   and add it as a positive match.
