# Redragon M913 Impact Elite — USB HID protocol notes

Factual reference for implementing `profiles/m913.ts` from scratch. This
document records only facts about the wire protocol (device IDs, byte
layouts, checksum arithmetic, lookup tables) — it does not reproduce any
source code. The TypeScript implementation should be written directly from
this document, not by translating any existing implementation line-by-line.

**Provenance**: these facts were read out of
[`m913-ctl`](https://github.com/Qehbr/m913-ctl) (GPL-3.0), which itself
states it reverse-engineered the protocol from USB captures and the
`mouse_m908` project. Protocol facts (device IDs, byte offsets, checksum
formulas, encoding tables) are not copyrightable expression, but if this
project is ever open-sourced, get this reasoning checked rather than assume
it.

## Device identification

Two hardware revisions exist in the wild; both need to be probed for.

| Revision | VID | PID (2.4G wireless receiver) | PID (wired / dual-mode) |
|---|---|---|---|
| Areson (original) | `0x25a7` | `0xfa07` | `0xfa08` |
| Compx (newer) | `0x3554` | `0xf55d` | `0xf55e` |

The two revisions use **different DPI and LED wire encodings** (see below) —
detect which one you're talking to from the VID before building any packet.

## Transport

The native tool talks to the device via `libusb` control transfers:

- `bmRequestType = 0x21` (host→device, class, interface)
- `bRequest = 0x09` (HID `SET_REPORT`)
- `wValue`:
  - Areson: `0x0308` → HID report type `3` (Feature), report ID `0x08`
  - Compx: `0x0208` → HID report type `2` (Output), report ID `0x08`
- `wIndex = 0x0001`
- Device→host responses come back on interrupt IN endpoint `0x82`.

**WebHID mapping (to verify against real hardware, not assumed)**: this
should correspond to `HIDDevice.sendFeatureReport(0x08, data)` for Areson
and `HIDDevice.sendReport(0x08, data)` for Compx, where `data` is the
16-byte payload *without* the leading `0x08` — WebHID's report-ID argument
likely replaces byte 0 of the raw packet described below, since the API
prepends/consumes the report ID itself rather than treating it as payload.
Responses should arrive via the `inputreport` event. This needs confirming
with a real device + `navigator.hid` before being treated as fact — it's an
inference from the libusb-level parameters, not an observed WebHID capture.

## Packet structure (17 bytes, host→device)

| Byte | Role |
|---|---|
| 0 | Always `0x08` (config command marker / report ID) |
| 1 | Sub-command: `0x07` = write data, `0x04` = finalize |
| 2 | Always `0x00` |
| 3 | Always `0x00` (except keyboard-key sub-packets, where it's an address byte) |
| 4 | Memory address byte (which block to write) |
| 5 | Payload length (bytes 6..5+len are meaningful) |
| 6–13 | Payload data |
| 14–15 | Padding, always `0x00` |
| 16 | Checksum (see below) |

Device→host response packets use report ID `0x09` at byte 0 instead of
`0x08`.

## Checksums

```
host → device:  byte[16] = (0x55 - sum(bytes[0..15])) & 0xFF
device → host:  byte[16] = (0x4C - sum(bytes[1..15])) & 0xFF   (byte[0] excluded)
```

Several commands below also carry an *inner* checksum on a sub-range of the
payload (e.g. `(0x55 - r - g - b) & 0xFF` for an RGB triplet) — those are
noted inline where they occur; they're separate from the outer byte[16]
checksum, which always covers the whole packet.

## Polling rate

One packet. Register address `0x0000`, length 2.

```
byte[4] = 0x00, byte[5] = 0x02
byte[6] = code       where 1000 Hz→0x01, 500 Hz→0x02, 250 Hz→0x04, 125 Hz→0x08
byte[7] = (0x55 - code) & 0xFF
```

## DPI — Areson hardware

DPI values are **not** arithmetic — they're a lookup table of
(value → 3-byte code). Only known-good values from the table can be set;
there is no formula to derive new codes. A representative subset (extend as
more values are needed):

```
100 →  00 00 55      1000 →  0b 0b 3f      4000 →  2f 2f f7      10000 →  77 77 67
200 →  02 02 51      1200 →  0d 0d 3b      5000 →  3b 3b df      12000 →  8f 8f 37
400 →  04 04 4d      1600 →  12 12 31      6400 →  4c 4c bd      14000 →  a7 a7 07
800 →  09 09 43      2000 →  17 17 27      8000 →  5f 5f 97      16000 →  bd bd db
```
(Full table has ~50 entries at non-uniform steps — see "Next steps" below
for where to source the complete set independently.)

5 DPI slots, packed two-per-packet across 3 packets, plus a 4th packet
carrying the enabled-slot bitmask:

- Packet 0: slot 1 at payload offset 6 (3 bytes, with a 1-byte `0x00` gap
  before the 3rd byte — i.e. bytes 6,7,_,9), slot 2 at offset 10 (same
  layout).
- Packet 1: slot 3 at offset 6, slot 4 at offset 10.
- Packet 2: slot 5 at offset 6 only (4-byte payload).
- Packet 3: enabled-slot control at bytes 6–7. Disabling cascades from the
  top — you can't disable an arbitrary slot, only "slot N and everything
  above it": `{e1,e2}` = `{0x05,0x50}` all 5 on, `{0x04,0x51}` top 4,
  `{0x03,0x52}` top 3, `{0x02,0x53}` top 2, `{0x01,0x54}` only slot 1. At
  least one slot must stay enabled.

A fixed sequence of 3 more packets ("unknown_2", addresses `0x2c`, `0x34`,
`0x3c`) must always follow the 4 DPI packets — their payload is constant
and not yet understood; treat them as an opaque required suffix for now.

## DPI — Compx hardware

Arithmetic, not table-based: `code = (dpi / 50) - 1`. Valid range 50–12750
in steps of 50 (`COMPX_DPI_MIN`/`MAX`/`STEP`).

One packet per slot, `addr = 0x0c + slot_index * 0x04`, payload
`[code, code, 0x00, inner]` where `inner = (0x55 - code - code) & 0xFF`.

Plus a stage-count packet at `addr = 0x02`: payload `[count, (0x55-count)&0xFF]`.
Compx also cascades from the top — count is "how many contiguous stages
starting at slot 1 stay enabled," same rule as Areson.

Compx also supports **per-slot DPI colors** (Areson does not): one packet
per slot at `addr = 0x2c + slot_index * 0x04`, payload
`[r, g, b, (0x55-r-g-b)&0xFF]`.

## LED

Four modes: Off / Steady / Respiration (breathing) / Rainbow.

- **Off**: one packet, address `0x58`, payload `[0x00, 0x55, 0, 0]`.
- **Steady**: one packet, address `0x54`. Payload: `r, g, b,
  (0x55-r-g-b)&0xFF, 0x01 (mode=steady), 0x54 (=0x55-0x01), brightness,
  (0x55-brightness)&0xFF`.
- **Respiration**: two packets. First (address `0x54`) carries color +
  mode=`0x02`, same layout as Steady but mode byte is `0x02`/checksum
  `0x53`, and bytes 12–13 carry brightness the same way. Second packet
  (address `0x5c`) carries speed: payload `[speed, (0x55-speed)&0xFF]`,
  speed range 1 (slowest) – 5 (fastest).
- **Rainbow**: two fixed packets (addresses `0x54` and `0x5c`) with no
  configurable parameters — constant payloads, not yet worth documenting
  further since there's nothing to compute.

## Button remapping

Deferred past the PoC (polling/DPI/LED prove out the transport + checksum
approach first). When it's picked up:

- 16 buttons, mapped via 8 packets (2 buttons per packet), addresses
  stepping by `0x08` from `0x60`. Even button index → payload offset 6,
  odd → offset 10, each a 4-byte action code.
- Action code format: `[function_type, modifier_bits, scancode, extra]`.
  `function_type` `0x81`–`0x8c` = mouse/DPI/special actions, `0x90` =
  single keyboard key, `0x91` = multi-key combo, `0x92` = multimedia key.
- Keyboard-key bindings additionally require separate "keyboard-key
  sub-packets" (per-button addresses in a lookup table) carrying HID
  usage-code down/up event sequences, capped at 3 modifiers+keys total.
- The full action-name → byte-code table (mouse buttons, DPI cycle, fire
  button, media keys, all keyboard scancodes) is a large lookup table, not
  a formula — extract it fact-by-fact the same way as this document when
  button remapping is implemented, from the same category of source (USB
  captures / existing reverse-engineering work), not by copying code.

## Open questions to verify against real hardware

1. Whether WebHID's `sendFeatureReport`/`sendReport` need the payload with
   or without a leading report-ID byte (see Transport section) — the
   `HIDDevice.collections` report descriptor, inspected at runtime, should
   settle this immediately once a browser is connected to a real M913.
2. Whether Chrome/Edge's WebHID implementation exposes the Areson feature
   report (`0x0308`) the same way `libusb`'s control transfer does, or
   whether the OS's own HID driver claims it first (this is the exact
   conflict the native app avoids via admin-elevated driver detachment —
   confirming WebHID doesn't hit the same wall is the first thing to test).
