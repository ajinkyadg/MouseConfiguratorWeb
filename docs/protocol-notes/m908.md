# Redragon M908 Impact — USB HID protocol notes

Factual reference for implementing `profiles/m908.ts` from scratch. Records
only facts about the wire protocol — no source code is reproduced. The
TypeScript implementation should be written directly from this document.

**Provenance**: these facts were read out of
[`mouse_m908`](https://github.com/dokutan/mouse_m908) (GPL-3.0), which
states its protocol knowledge comes entirely from reverse-engineering.
Read directly from the raw source files (not a third-party summary) for
accuracy — control-transfer parameters, byte offsets, and the DPI/light
mode/report-rate lookup tables below are transcribed numeric facts, not
copied code. Device IDs, byte offsets, and lookup tables are not
copyrightable expression, but if this project is ever open-sourced, get
this reasoning checked rather than assume it (same caveat as `m913.md`).

**Now covered**: button/key mapping encoding (see below) — implemented in
`profiles/m908-buttons.ts`. **Still not covered**: macro *storage*
(recording a custom multi-step macro into one of the 15 onboard slots) —
a button can *reference* a macro slot (see "macro" action below), but
writing the macro's own keystroke sequence isn't implemented.

## Device identification

| | VID | PID |
|---|---|---|
| M908 Impact | `0x04d9` | `0xfc4d` |

Unconfirmed whether the M908 has a separate wireless-receiver PID the way
the M913 does (Areson `0xfa07` wireless vs `0xfa08` wired) — only one PID
is documented in the reference project. Treat wireless-only operation as
unverified until tested.

## Transport

Settings are written via a **USB control transfer**, not `sendReport`:

```
bmRequestType = 0x21   (host-to-device, class, interface recipient)
bRequest      = 0x09   (SET_REPORT)
wValue        = 0x0302 (report type 0x03 = Feature, report ID 0x02)
wIndex        = 0x0002 (interface 2)
```

This maps directly to WebHID's `sendFeatureReport(reportId, data)`:
reportId = `0x02`. Byte 0 of every default template row transcribed into
`m908-tables.json` is consistently `0x02`, matching `wValue`'s report-ID
byte exactly — strong evidence (though not yet hardware-confirmed) that,
same as the M913, byte 0 is the report-ID marker and should be stripped
before calling `sendFeatureReport(reportId, payload)`, not included
twice. `m908.ts`'s `toFeatureReportPayload()` assumes this. Confirm
against a real device before shipping a UI against this.

## Packet structure: three settings blocks

Unlike the M913's single 17-byte-packet-per-setting model, applying
settings sends **three separate blocks** in sequence, each covering
different fields, all for **5 profiles** at once (M908 has onboard
profile storage, unlike M913's single active config):

- **Block 1**: N × 16-byte packets (light mode, color, brightness, speed,
  report rate)
- **Block 2**: one 64-byte packet (scroll speed only)
- **Block 3**: N × 16-byte packets (DPI enable/value, key mapping — key
  mapping not decoded, see above)

Each packet is sent as its own `sendFeatureReport(0x02, packet)` call, in
sequence — no combined checksum across packets was found (no checksum
byte at all was identified in the reference source; unlike M913, these
packets appear to have no per-packet checksum).

## Block 1 offsets (16-byte packets), per profile `i` (0-4)

| Field | Packet index | Byte offset(s) |
|---|---|---|
| Light mode | `3 + 2*i` | bytes 11 and 13 (2-byte code, see table below) |
| Color (R,G,B) | `3 + 2*i` | bytes 8, 9, 10 |
| Speed | `3 + 2*i` | byte 12 |
| Brightness | `4 + 2*i` | byte 8 |
| Report rate, profiles 0-2 (`i` = 0,1,2) | packet 13 | byte `8 + 2*i` (bytes 8, 10, 12) |
| Report rate, profiles 3-4 (`i` = 3,4) | packet 14 | byte `2 + 2*i` (bytes 8, 10 — **not** 2, 4; an earlier draft of this table miscalculated this) |

## Block 2 offset (64-byte packet)

| Field | Byte offset(s) |
|---|---|
| Scroll speed, per profile `i` (0-4) | byte `8 + 2*i` |

## Block 3 offsets (16-byte packets), per profile `i` (0-4), DPI stage `j` (0-4)

| Field | Packet index | Byte offset(s) |
|---|---|---|
| DPI stage enabled | `7 + 5*i + j` | byte 8 (boolean 0/1) |
| DPI stage value (2-byte code) | `7 + 5*i + j` | bytes 9, 10 |

## Report rate encoding (byte -> Hz)

Confirmed shared across the whole `mouse_m908` device family (not
M908-specific):

| Byte | Rate |
|---|---|
| `0x08` | 125 Hz |
| `0x04` | 250 Hz |
| `0x02` | 500 Hz |
| `0x01` | 1000 Hz |

## Light mode encoding (2-byte code)

Also shared across the device family:

| Bytes | Mode |
|---|---|
| `0x00, 0x00` | Off |
| `0x01, 0x01` | Breathing rainbow |
| `0x01, 0x02` | Static |
| `0x01, 0x04` | Breathing |
| `0x01, 0x08` | Rainbow |
| `0x01, 0x10` | Flashing |
| `0x02, 0x00` | Wave |
| `0x03, 0x00` | Reactive (button) |
| `0x04, 0x00` | Random |
| `0x06, 0x00` | Alternating |
| `0x07, 0x00` | Reactive |

## DPI encoding: fixed lookup table, not a formula

Confirmed from source: DPI-to-byte-code is a **lookup table**, not an
arithmetic formula (ruled out — the byte deltas between consecutive 100
DPI steps aren't constant). 200-6200 DPI in 100-unit steps, then
6400-12400 DPI in 200-unit steps (the second byte becomes `0x01`,
completing a second cycle of the same first-byte progression seen in the
first half — effectively byte 2 flags which "cycle" the value is in).

## Button mapping

**Provenance**: the encode function (`_i_encode_button_mapping`) and the
shared lookup tables below live in `rd_mouse.cpp`/`data.cpp` — shared
across the whole `mouse_m908` device family (transcribed into
`redragon-family-keycodes.json`, not `m908-tables.json`, since it isn't
M908-specific and is expected to be reused for M719).

**20 physical button slots** (`m908-tables.json`'s `buttonNames`, in
index order 0-19): left, right, middle, fire, dpi_up, dpi_down, button_1
through button_12, scroll_up, scroll_down.

**Write location**: settings block 3, packet index `35 + 20*i + j` for
profile `i` (0-4) and button slot `j` (0-19), the 4 mapping bytes at byte
offsets 8, 9, 10, 11.

**Every M908/M719 keyboard key value is a standard USB HID keyboard
usage code** — confirmed identical to the values already in
`m913-button-tables.json`'s `keyCodes` (e.g. `a`=0x04, `c`=0x06,
`tab`=0x2b, `enter`=0x28, `arrow_left`=0x50) — reuse that table directly
rather than duplicating it.

The 4-byte mapping encodes one of several distinct action kinds,
determined by byte 0:

| Byte 0 | Meaning |
|---|---|
| a value from **`specialActions`** (`redragon-family-keycodes.json`) | mouse buttons, DPI/profile/report-rate step, media keys, OS "compatibility" shortcuts (cut/copy/paste/etc.) — each is a full fixed 4-byte value, looked up by name, not composed |
| `0x90` | plain keyboard key, byte 2 = HID usage code, bytes 1/3 = 0 |
| `0x8f` | keyboard key **with modifier(s)**, byte 1 = sum of `keyboardModifierValues` bits (ctrl_l=1, shift_l=2, alt_l=4, super_l=8, ctrl_r=16, shift_r=32, alt_r=64, super_r=128 — multiple modifiers OR together), byte 2 = HID usage code |
| `0x99` | **fire** (repeated keypress): byte 1 = key code (`0x81`/`0x82`/`0x84` for mouse left/right/middle, or a HID usage code), byte 2 = repeat count, byte 3 = delay |
| `0x9a` | **snipe** (DPI override while held): byte 1 = `0x01`, bytes 2 and 3 = the same snipe-DPI byte (`snipeDpiValues` table — only 200-1100 DPI in 100-steps are defined in the reference source, unlike the full main DPI table) |
| `0x91` | **macro reference**: byte 1 = macro slot index (0-14), byte 2 = repeat count (`0x00`=no-repeat/once via a separate no-repeat encoding, see source), byte 3 = `0x00`. Two special byte-1 encodings exist for "repeat until pressed again" (`slot + 0x3f`) and "repeat while held" (`slot + 0x7f`), both pairing with bytes 2,3 = `0xff, 0xff`. Writing the macro's own recorded content is not implemented here (see above). |

## Open questions (block on real hardware before shipping a UI for this)

- Whether payload byte 0 needs to repeat the report ID (see Transport
  section) — affects how `sendFeatureReport` should be called.
- Button/key mapping encoding and the 20-slot `_c_button_names` list —
  not researched in this pass.
- Whether a wireless-receiver PID exists separately from `0xfc4d`.
- Whether these packets need any inter-packet delay (M913 required none
  found so far, but this protocol's multi-block sequential-write shape is
  different enough to not assume the same).
